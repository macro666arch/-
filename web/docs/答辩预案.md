# 答辩 Q&A 预案（20 问）

> 用途：答辩前统一口径。每题先记一句话，再用证据展开。  
> 原则：只把已经实现和验证过的能力说成“已完成”；微信/飞书机器人、多智能体独立编排尚未上线，要主动说边界。

## 一、定位与差异

### Q1：大模型已经能回答很多问题，为什么还要做这个？

**一句话**：校园场景最贵的不是“生成一段话”，而是**说错一个电话、日期或材料后的后果**。

展开：

- 通用模型可能给出格式正确但未经核验的号码和截止日期。
- 官网本身会出现电话冲突、旧制度未下线、流程跳号、附件空壳和缺字段。
- 我们把“答案是否可信”变成可检查的数据结构，而不是让模型自己说“我很确定”。

### Q2：这和学校官网搜索框有什么区别？

**一句话**：搜索框给链接，我们给**带状态、证据和下一步动作的结论**。

官网搜索框通常只能返回多个页面。本系统会：

1. 找到与问题相关的官方来源；
2. 判断是已核实、存在冲突，还是原文缺字段；
3. 把结果整理成办事卡；
4. 把办事卡转成本机任务、倒计时和补救路径。

### Q3：为什么从“问答”继续做任务闭环？

**一句话**：学生真正要的不是一段答案，而是**在截止前把事办完**。

普通问答停在“告诉你怎么办”。我们的五个动作是：

`查信息 → 办事卡 → 加入任务 → 截止提醒 → 错过补救`

这使系统从一次性的信息工具，变成可以每天使用、刷新后仍保留的办事助手。

### Q4：你们最核心的创新点是什么？

**一句话**：把“可信问答”与“可执行任务”连成一条可验证的链路。

具体有三层：

- **可信层**：三态判定、官方来源、原文摘录、域名白名单；
- **行动层**：截止、材料、步骤、入口、部门电话；
- **连续层**：本机任务、完成度、临期提醒、逾期和补救路径。

## 二、技术实现

### Q5：三态是谁判定的？是模型自己说“不确定”吗？

**一句话**：不是模型自评，是**确定性规则和数据字段共同判定**。

判定顺序：

1. 检索到两个以上互相矛盾的权威说法 → `conflict`；
2. 命中条目但关键字段为空、附件不可用或原文缺口 → `unconfirmed`；
3. 有唯一可用官方依据且关键字段齐全 → `answered`。

模型可以负责把结构化事实写成自然语言，但不能绕过状态和证据约束。

### Q6：那大模型具体做了什么？是不是可以不要模型？

**一句话**：模型负责“把结构化事实讲清楚”，状态、来源和数值不能交给模型自由生成。

模型适合做：

- 将字段组织成学生看得懂的段落；
- 把官方步骤整理成更易读的顺序；
- 根据已核验结果生成追问建议。

电话、日期、金额、材料名称和官方步骤仍必须从知识库字段来。

### Q7：办事卡是怎么生成的？

**一句话**：办事卡是**官方字段的结构化投影**，不是另写一段营销文案。

办事卡包含：

- 来源类型和来源 ID；
- 标题、适用对象和摘要；
- 截止时间、部门、电话、地点、服务时间、入口；
- 所需材料和附件状态；
- 步骤，并区分 `official`（官网原文）和 `derived`（系统整理）；
- `missing_fields`（原文未明确项）；
- `remedy`（错过后的路径）；
- 核验状态和官方原文链接。

### Q8：官网没有写截止日期时，你们怎么处理？

**一句话**：不猜日期，显示**“官方原文未明确”**并给核实渠道。

例如选课通知只写了“分两轮”，却没有给出具体起止日期。系统不会根据“大概是开学第二周”生成日期，而是把缺口放在办事卡顶部，并提示登录教务系统或联系教学运行中心核实。

### Q9：任务保存在哪里？刷新就丢吗？

**一句话**：任务保存在当前浏览器的 `localStorage`，刷新页面仍保留，但换设备不同步。

已验证：

- 加入任务成功；
- 勾选步骤后完成度更新；
- 刷新后任务和勾选状态仍在；
- 可复制微信/飞书摘要；
- 可下载带提前 24 小时提醒的 `.ics`。

### Q10：已经截止的事情，系统能做什么？

**一句话**：不编造补报名，只给**可核实的候补或人工补救路径**。

以 2026 年下半年四六级报名为例：

- 官方报名时间为 2026-09-15 10:00 至 2026-09-28 17:00；
- CET6 分两阶段报名；
- 当前日期已经超过报名截止；
- 官方未公布统一补报名；
- 系统给出报名系统自动候补和本科生院教学运行中心 `65779333` 的核实路径。

### Q11：你们接的是哪个模型？

**一句话**：当前演示基线是**确定性本地引擎 + 可切换后端检索流水线**，不把模型名当成产品卖点。

前端可以本地运行，也可以在 `NEXT_PUBLIC_USE_MOCK=false` 时调用 NestJS 后端。后端包含检索、核验和规划阶段；接大模型时，三态契约、证据结构和测试规则保持不变。

## 三、数据与测试

### Q12：56 题是谁出的？自己出题自己考不是必然通过吗？

**一句话**：题目先写、引擎后改，而且我们主动承认这是**团队自测**，不是独立第三方评测。

当前结果：

- 56/56 通过；
- 33 题有依据；
- 2 题冲突；
- 21 题无法确认。

期望状态来自对官网的实测结论，不是按“系统能答什么”反推。严格来说，这套测试仍缺少外部出题和盲测，这是后续最应该补的验证。

### Q13：21 题无法确认，拒答率这么高是不是能力差？

**一句话**：拒答不是在偷懒，而是把“官网没写”与“系统没查到”分开。

典型原因：

- 官方原文确实没有写（例如选课具体日期、休学年限）；
- 官网两处电话冲突；
- 通知附件为空壳或无法读取；
- 问题超出校园公开信息范围（个人绩点、食堂今日菜单、其他学校政策）。

好的拒答必须同时给出核实渠道，而不是只说“不知道”。

### Q14：官方缺陷总数是怎么来的？

**一句话**：来自知识库 `gaps` 等字段的动态统计，不是手写在首页的宣传数字。

页面会汇总冲突、缺字段、附件异常、步骤跳号和入口失效等问题。答辩时可以直接打开首页或流程页，说明这些记录都能回到来源页面核对；如果数据变化，统计也会变化。

## 四、平台与后续路线

### Q15：你们现在真的接入微信或飞书了吗？

**一句话**：**没有接入机器人；当前完成的是微信/飞书可粘贴的任务摘要导出**。

当前实际能力：

- 生成适合粘贴到群聊的办事摘要；
- 用户可把摘要发到微信或飞书；
- 任务是本机保存，不会自动同步到群聊。

真实接入需要下一步：

1. 飞书自定义机器人或企业自建应用；
2. webhook 签名校验和权限控制；
3. 后端查询 API 与卡片消息格式；
4. 用户身份、数据权限和审计。

### Q16：为什么选择自己做，而不是全放在 Dify？

**一句话**：Dify 适合快速编排，但我们的核心价值在**证据结构、确定性核验和任务状态**，这部分需要代码控制。

平台分工建议：

- **当前 Next.js + NestJS**：最终产品、复杂规则、任务闭环、可演示界面；
- **Dify / Coze**：快速验证多节点提示词流程和知识库问答；
- **飞书机器人**：做群内查询和卡片消息入口；
- **Trae**：AI 辅助写代码的 IDE，不是运行时平台，不能替代后端。

推荐先用飞书做一个只读查询入口，稳定后再增加“创建任务”和“提醒”动作。

### Q17：你们算多智能体吗？

**一句话**：当前是**单入口的检索、核验、规划流水线**，还不是独立部署的多智能体系统。

可以沿职责拆成：

- 检索 Agent：多表查询和召回；
- 核验 Agent：检查来源、冲突、缺口和有效性；
- 规划 Agent：生成办事卡和补救路径；
- 通知 Agent：飞书/日历提醒；
- 审计 Agent：记录数据更新和人工复核。

拆分的价值是让每一步可观测、可替换，而不是只在架构图上画更多节点。

## 五、边界与收尾

### Q18：为什么不直接做 App？

**一句话**：比赛阶段网页链接的分发和迭代成本最低，扫码或点链接即可使用。

网页可以更新即生效，不需要应用商店审核，也能在手机浏览器和微信内置浏览器打开。后续如果验证了高频使用，再考虑小程序或 App。

### Q19：官网改版、数据过期怎么办？

**一句话**：当前是阶段性快照，系统会把“待核实”显式展示，后续应增加定时复核和过期自动降级。

已经保留：

- `source_url`；
- `last_verified_at`；
- `verify_status`；
- `effective_status`；
- 原文缺口字段。

尚未实现的是自动抓取、变更检测和超期自动降级。

### Q20：如果多一个月，你们优先做什么？

**一句话**：优先做**飞书只读入口 + 数据过期复核 + 第三方盲测**，而不是继续堆页面。

顺序：

1. 飞书自定义机器人接入查询和任务摘要；
2. 官网变更检测、过期自动降级；
3. 让不认识项目的人出题做外部测试；
4. 再考虑把检索、核验、规划拆成可观测的多个 Agent。
