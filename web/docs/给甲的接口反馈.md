## 零、2026-11-03 C5 飞书协议确认

新版协议已经明确：前端只调用

```text
POST /api/integrations/feishu/task
Content-Type: application/json

{ "text": "要推送的完整文本" }
```

前端不会调用 `/api/feishu/push-task` 或 `/api/feishu/remind`，也不会传 Webhook 地址。
任务页已经接入手动单向推送，并处理 `sent` / `not_configured` / `provider_error` 三种结果。

还需要后端统一一处状态码：当前 `campus-integrations.service.ts` 仍可能返回
`invalid_config`，但新版协议只列了 `not_configured` 和 `provider_error`。
前端为了兼容旧后端，会把 `invalid_config` 暂时收敛为 `not_configured`；
建议后端把“Webhook 未配置 / 配置不合法”统一为 `not_configured`，把飞书请求失败统一为 `provider_error`。

群内输入关键词后自动回复还需要事件回调路由、challenge 校验、消息事件格式和回复接口，
不属于本次单向 Webhook 推送范围。

## 一、`GET /api/policies` 没有列进 §2.4 🔴

**问题**：契约 §1.3 定义了 `policy` 表的字段，但 §2.4 的端点表里**没有对应的 GET 接口**。
前端的「规章制度」页需要列 6 份规定，现在只能读本地数据。

**影响**：如果后端不提供，合并后规章制度页显示的是我这边的快照，
不是乙产出的 `policy.json`——**两边的数据会不一致**。

**建议**：照其他列表接口补一个，形状一致：

```json
GET /api/policies
{ "items": [ /* policy 记录，字段同 §1.3 */ ], "total": 6 }
```

前端已经预留好了，你加完我改一行就能接（`src/lib/api.ts` 里的 `fetchPolicies`）。

## 二、`GET /api/calendar` 的返回缺通用字段 ⚠️

契约 §2.4 的示例是：

```json
{
  "academic_year": "2026-2027",
  "semester": "秋",
  "teaching_weeks": "1-17",
  "exam_weeks": "18-19",
  "daily_schedule": { "第一节": "8:00" }
}
```

**问题**：
1. 缺 `id` / `source` / `source_url` / `verify_status` / `effective_status`。
   其他表都是「知识库记录」，有来源可回溯；calendar 这样就变成了**没有出处的一手数据**。
   界面上「来源」卡片没内容可显示。
2. `teaching_weeks: "1-17"` 是字符串，`daily_schedule` 是对象 —— 和其他表的形状风格不一致。

**我这边已经处理了**（不阻塞）：
`src/lib/api.ts` 的 `normalizeCalendar()` 会把 `"1-17"` 转成 `{start:1,end:17}`、
把 `{"第一节":"8:00"}` 转成 `[{period,time}]`；
缺的通用字段补默认值，并在 `gaps` 里写明「契约 §2.4 未定义 xxx」，
界面上显示成橙色提示，不会出现 `undefined`。

**建议**：如果校历是从教务处页面抓的，就给个 `source_url`；
实在给不出，也请在 `gaps` 里写一句「校历无稳定官方页面」，我在界面上照实展示。

## 三、`status=conflict` 时请务必给 `conflicts` 数组 🟡

契约 §2.2 写的是「answer 里展示冲突双方 + 各自来源」。
如果只写在 `answer` 的正文里，前端只能当纯文本渲染。

我这边做了并列卡片（两个号码左右分开、各带来源链接），需要结构化数据：

```json
{
  "status": "conflict",
  "conflicts": [
    { "label": "教务处页面", "value": "65783223",
      "source": "教务处", "source_url": "https://jwc.cuc.edu.cn/jwcyx/list.htm" },
    { "label": "信息化处页面", "value": "65773223",
      "source": "信息化处", "source_url": "https://its.cuc.edu.cn/xskyqblzn/list.htm" }
  ]
}
```

`conflicts` 是**可选字段**，不给也不会崩（会退化成只显示 `answer` 文字），
但并列卡片是这个项目最有说服力的部分，建议给。

## 五、自检脚本

我写了个联调自检，你那边起了服务之后可以直接跑：

```bash
node scripts/probe.mjs                          # 打 localhost:3001
node scripts/probe.mjs http://你的地址:端口
```

它逐项检查 7 个端点的连通性、`{items,total}` 形状、关键字段是否齐全，
输出「可以接了」或「哪几行有问题」。**不用你手动一个个 curl。**
